## 1. Постановка задачи

В рамках лабораторной работы №1 требовалось по выбранному варианту выполнить вёрстку сайта средствами HTML, CSS и Bootstrap, а также продумать и реализовать те моменты, где действительно необходим JavaScript (например, открытие модальных окон).

Выбранный вариант №5 — **«Сервис для обмена рецептами и кулинарных блогов»** — включает следующие возможности:

- вход;
- регистрация;
- личный кабинет пользователя (сохранённые рецепты, публикации);
- поиск рецептов с фильтрацией по типу блюда, сложности, ингредиентам;
- страница рецепта с фото, пошаговыми инструкциями и видео;
- социальные функции (комментарии, лайки, подписки на кулинаров).

Каждый сайт **обязательно** должен включать следующие страницы:

- вход;
- регистрация;
- личный кабинет пользователя;
- страница для поиска с возможностью фильтрации.

### Что осознанно НЕ входило в ЛР1

Поскольку это первая работа из цикла, взаимодействие с реальным API не требовалось: все данные — это статические заглушки, а состояние (сессия, лайки, закладки, подписки, локально созданные рецепты и комментарии) хранится в `localStorage` браузера. Полноценная интеграция с моковым JSON-сервером через `fetch`/`axios` и авторизация по токену — это уже задача ЛР2.

## 2. Краткое резюме выполненной работы

Реализован полноценный многостраничный статический сайт из **6 HTML-страниц**, связанных единой навигацией:

| № | Страница | Файл | Назначение |
|---|---|---|---|
| 1 | Главная | `index.html` | Приветственный блок, лента популярных рецептов, блок кулинаров |
| 2 | Вход | `pages/login.html` | Форма входа с валидацией |
| 3 | Регистрация | `pages/register.html` | Форма регистрации с валидацией |
| 4 | Личный кабинет | `pages/profile.html` | Профиль, публикации, сохранённые, подписки, модалки |
| 5 | Поиск | `pages/search.html` | Фильтрация и сортировка рецептов |
| 6 | Рецепт | `pages/recipe.html` | Карточка рецепта, шаги, видео, лайки, комментарии |

Функциональная часть вынесена в **8 ES-модулей** (`assets/js/`), стили — в **2 CSS-файла** с CSS-переменными, графика — в **SVG-спрайт** (15 иконок) и **SVG-заглушку** изображения. Bootstrap 5.3.8 подключён **локально** (файлы лежат в репозитории), сторонние CDN не используются.

JavaScript применён именно там, где без него не обойтись:

- рендер карточек рецептов и карточек авторов из данных;
- клиентская валидация форм входа и регистрации;
- фильтрация и сортировка рецептов в реальном времени;
- лайки, сохранения (закладки), подписки и комментарии;
- модальные окна Bootstrap (новый рецепт, редактирование профиля, «Поделиться»);
- синхронизация шапки сайта с состоянием авторизации;
- «защита» страницы личного кабинета от неавторизованных пользователей.

## 3. Используемый стек и обоснование выбора

| Технология | Версия | Как подключена | Почему так |
|---|---|---|---|
| HTML5 | — | Статические `.html`-файлы | Семантическая разметка, доступность, нативные формы |
| CSS3 | — | `assets/css/variables.css`, `assets/css/style.css` | CSS-переменные и минимальный кастомный слой поверх Bootstrap |
| Bootstrap | 5.3.8 | Локально: `assets/vendor/bootstrap/bootstrap.min.css` и `bootstrap.bundle.min.js` | Готовая адаптивная сетка, навбар, карточки, табы, модалки, формы |
| JavaScript | ES2020+ (ES-модули) | `<script type="module">` | Компонентная организация без сборщиков и внешних зависимостей |

### Почему Bootstrap подключён локально

Файлы Bootstrap скачаны в репозиторий, а не подключены с CDN. Это даёт:

1. **Работу без интернета** — сайт полностью автономен, что удобно для демонстрации на защите.
2. **Воспроизводимость** — фиксированная версия 5.3.8, сайт не сломается из-за изменений на CDN.
3. **Соответствие духу задания** — демонстрирует умение подключать фреймворк, а не только ссылаться на него.

Используется именно `bootstrap.bundle.min.js` (а не отдельный `bootstrap.min.js`), потому что bundle уже содержит Popper.js, необходимый для работы выпадающих меню (`dropdown`) и всплывающих подсказок.

### Почему JavaScript написан на нативных ES-модулях

Задание ЛР1 требует JS «там, где он нужен». Вместо jQuery и сборщиков (webpack/vite) выбран современный подход:

- `import`/`export` — нативная модульность браузера;
- нет `node_modules`, нет этапа сборки — проект запускается одним `http.server`;
- каждый модуль отвечает за одну зону ответственности (данные, хранилище, авторизация, рендер, соц. функции).

Единственное следствие — страницы нельзя открывать двойным кликом по файлу (браузер заблокирует импорт модулей с `file://`), нужен локальный веб-сервер. Это описано в `README.md`.

## 5. Архитектурные принципы

### 5.1. Разделение ответственности по модулям

Ключевая идея архитектуры — каждый JS-модуль отвечает ровно за одну вещь, и модули образуют понятную цепочку зависимостей:

```
data.js        (чистые данные + справочники)
   ↑
storage.js     (персистентность: localStorage)
   ↑
main.js        (общие утилиты: пути, escapeHtml, форматирование, пользователь, навигация, модалки)
   ↑
auth.js   recipes.js   social.js   profile.js   recipe.js   (страничная логика)
```

- **`data.js`** не знает ни о DOM, ни о хранилище — только данные и функции поиска.
- **`storage.js`** — единственная точка доступа к `localStorage`; ни один другой модуль не обращается к `localStorage` напрямую.
- **`main.js`** — «общий знаменатель»: то, что нужно почти всем (корень проекта, экранирование, формат даты/времени, текущий пользователь, состояние шапки).
- Страничные модули (`auth`, `recipes`, `social`, `profile`, `recipe`) подключаются только на тех страницах, где они нужны.

### 5.2. Одна страница — набор подключаемых модулей

Каждая HTML-страница подключает только те модули, которые ей нужны. Например:

| Страница | Подключённые модули |
|---|---|
| `index.html` | `main.js`, `recipes.js`, `social.js` |
| `login.html`, `register.html` | `main.js`, `auth.js` |
| `search.html` | `main.js`, `recipes.js` |
| `profile.html` | `main.js`, `auth.js`, `recipes.js`, `profile.js` |
| `recipe.html` | `main.js`, `recipe.js`, `social.js` |

Это уменьшает «вес» страницы и исключает выполнение ненужного кода.

### 5.3. Прогрессивное улучшение через `hidden`

Почти весь динамический контент в HTML заранее помечен атрибутом `hidden` и включается только после того, как JS его заполнит. Например, блок рецепта:

```html
<article data-recipe-view hidden>
```

Это защищает от «мигания» пустых блоков до инициализации скриптов. Аналогично устроены состояния авторизации в шапке (`data-auth-guest` / `data-auth-user`), предупреждения для неавторизованных и т.п.

### 5.4. Инициализация по `DOMContentLoaded`

Каждый модуль в конце файла навешивает обработчик:

```js
document.addEventListener('DOMContentLoaded', init);
```

Благодаря этому модули не зависят от порядка подключения в HTML: к моменту их выполнения DOM уже построен. Внутри `init()` каждый модуль сам проверяет, есть ли на странице нужные ему элементы, и если нет — просто выходит. Поэтому один и тот же модуль безопасно подключать на разные страницы.

### 5.5. Связь HTML и JS через `data-*`-атрибуты

Вместо жёстких CSS-классов или id JS опирается на `data-`-атрибуты:

- `data-root` — корень проекта (см. ниже);
- `data-auth-guest`, `data-auth-user`, `data-auth-username`, `data-logout` — состояние авторизации;
- `data-recipes-list`, `data-search-results`, `data-profile-published` и др. — контейнеры для рендера;
- `data-like-recipe`, `data-bookmark-recipe`, `data-subscribe-author` — кнопки действий;
- `data-search-form`, `data-comment-form`, `data-new-recipe-form` — формы.

Это делает разметку и логику слабо связанными: JS не «цепляется» за визуальные классы Bootstrap, которые могут меняться.

## 6. Подробный разбор страниц

### 6.1. Главная страница (`index.html`)

**Назначение:** точка входа, знакомство с сервисом, демонстрация ленты рецептов.

**Структура:**

1. **Шапка** (`<header><nav>`) — единая для всех страниц. Содержит логотип-бренд `RecipeHub`, адаптивное меню-«бургер» (Bootstrap `navbar-expand-lg` + `navbar-toggler` + `collapse`), пункты «Главная» и «Поиск рецептов», а также два взаимоисключающих блока состояния:
   - `data-auth-guest` — кнопки «Вход» и «Регистрация»;
   - `data-auth-user` — выпадающее меню с иконкой пользователя, именем и кнопкой «Выйти».
2. **Приветственный блок** — заголовок `<h1>`, лид-абзац, кнопки «Найти рецепт» и «Присоединиться», а также **форма быстрого поиска**.
3. **Секция «Популярные рецепты»** — контейнер `data-recipes-list="6"`, который заполняется модулем `recipes.js` шестью самыми популярными рецептами.
4. **Секция «Популярные кулинары»** — три статические карточки авторов с кнопками «Подписаться» (`data-subscribe-author`).
5. **Подвал** (`<footer>`) — название проекта, пометка об учебном характере и навигационные ссылки.

**Важная деталь — форма быстрого поиска.** Она отправляет GET-запрос на страницу поиска:

```html
<form class="card card-body shadow-sm" role="search" action="pages/search.html" method="get">
  <input class="form-control" type="search" id="home-search" name="query" ...>
```

При отправке браузер сам сформирует адрес вида `pages/search.html?query=паста`. Страница поиска затем читает этот параметр (`recipes.js`, `initSearchPage`) и подставляет его в поле «Название или описание» — то есть быстрый поиск с главной реально работает, без единой строчки JS.

**Лента рецептов** (`recipes.js`, `initHomePage`):

```js
const limit = Number(container.dataset.recipesList) || getAllRecipes().length;
const popular = [...getAllRecipes()]
  .sort((a, b) => b.likes - a.likes)
  .slice(0, limit);
renderRecipes(container, popular);
```

Число `6` берётся прямо из атрибута `data-recipes-list="6"` — разметка управляет тем, сколько карточек показать.

   - `#newRecipeModal` — форма создания рецепта (`data-new-recipe-form`);

### 6.5. Страница поиска (`pages/search.html`)

**Назначение:** поиск рецептов с фильтрацией и сортировкой — одна из обязательных страниц по заданию.

**Разметка:** двухколоночная сетка (`col-12 col-lg-3` + `col-12 col-lg-9`).

- **Левая колонка — панель фильтров** (`form data-search-form`), закреплённая при прокрутке на больших экранах (`sticky-lg-top`):
  - «Название или описание» — `input[type=search]`, `name="query"`;
  - «Тип блюда» — `select` с `data-filter="dishType"` (варианты подставляются из JS);
  - «Сложность» — `select` с `data-filter="difficulty"` (варианты из JS);
  - «Ингредиент» — текстовое поле `name="ingredient"`;
  - «Время, не более» — `select` со значениями 15/30/60/120 минут;
  - кнопки «Применить» (submit) и «Сбросить» (`data-search-reset`).
- **Правая колонка — результаты:**
  - счётчик `data-search-counter` с `aria-live="polite"` (озвучивается скринридером при изменении);
  - селектор сортировки, связанный с формой через атрибут `form="search-form"`;
  - контейнер `data-search-results` для карточек.

**Ключевая особенность — «живая» фильтрация.** Обработчики `input`/`change` навешиваются на все поля формы, поэтому результаты пересчитываются сразу при вводе/изменении, без нажатия «Применить»:

```js
Array.from(form.elements).forEach((control) => {
  control.addEventListener('input', applyFilters);
  control.addEventListener('change', applyFilters);
});
```

Кнопка «Применить» при этом тоже работает (вызывает `applyFilters` по submit).

### 6.6. Страница рецепта (`pages/recipe.html`)

**Назначение:** детальный просмотр одного рецепта — фото, описание, ингредиенты, пошаговые инструкции, видео, лайки, сохранение, комментарии и блок автора.

**Разметка:**

2. **`<article data-recipe-view hidden>`** — основное содержимое:

## 7. Разбор JavaScript-модулей

### 7.1. `data.js` — данные-заглушки

Содержит всё «наполнение» сайта, описанное статически:

- `DISH_TYPES` — справочник типов блюд: «Салаты», «Супы», «Основные блюда», «Выпечка», «Десерты», «Напитки»;
- `DIFFICULTIES` — «Низкая», «Средняя», «Высокая»;

- `recipes` — 8 рецептов с полями `id`, `title`, `authorId`, `dishType`, `difficulty`, `timeMinutes`, `servings`, `description`, `ingredients[]`, `steps[]`, `image`, `likes`, `videoUrl`, `createdAt`;

- функции поиска: `getUserById(id)`, `getRecipeById(id)`, `getCommentsByRecipe(recipeId)`.

Структура данных намеренно приближена к тому, что вернул бы реальный API (например, `authorId` — это ссылка на сущность, а не имя автора), чтобы в ЛР2 модуль можно было заменить на запросы к JSON-серверу с минимальными правками.

### 7.2. `storage.js` — обёртка над localStorage

Единственное место, где код работает с `localStorage`. Все ключи собраны в объект `KEYS`:

```js
const KEYS = {
  session: 'rh_session',
  users: 'rh_users',
  profileOverrides: 'rh_profile_overrides',
  recipes: 'rh_recipes',
  likes: 'rh_likes',
  bookmarks: 'rh_bookmarks',
```

Внутренние функции `read(key, fallback)` и `write(key, value)` оборачивают `JSON.parse`/`JSON.stringify` в `try/catch` — при повреждённых данных или недоступности хранилища приложение не падает, а пишет предупреждение в консоль и возвращает запасное значение.

Публичный API: сессия (`getSessionUserId`, `setSessionUserId`, `clearSession`), локальные аккаунты (`getLocalUsers`, `addLocalUser`), правки профиля (`getProfileOverrides`, `saveProfileOverride`), локальные рецепты (`getLocalRecipes`, `addLocalRecipe`), лайки (`getLikes`, `toggleLike`), закладки (`getBookmarks`, `toggleBookmark`), подписки (`getSubscriptions`, `toggleSubscription`), комментарии (`getLocalComments`, `addComment`) и утилита `resetAll()` для полной очистки состояния при отладке.

### 7.3. `main.js` — общий модуль

Четыре группы функций:

1. **Пути.** `root()` читает `data-root` у `<body>`, `url(relativePath)` собирает путь от корня. Это решает проблему разных глубин вложенности страниц (см. [раздел 8.1](#81-пути-к-ресурсам-и-data-root)).
2. **Безопасность.** `escapeHtml(value)` экранирует `&`, `<`, `>`, `"`, `'` — применяется ко всему пользовательскому тексту перед вставкой через `innerHTML` (защита от XSS).
3. **Форматирование.** `formatDuration(minutes)` превращает 90 в «1 ч 30 мин», `formatDate(isoDate)` — в дату формата `ДД.ММ.ГГГГ` через `toLocaleDateString('ru-RU')`.
4. **Пользователь и навигация.**
   - `getAllUsers()` — объединяет статических пользователей и локально зарегистрированных, накладывая правки профиля;

   - `getCurrentUser()` — определяет текущего пользователя по id из сессии;
   - `getUserName(authorId)` — имя автора по id;
   - `markActiveNavLink()` — подсвечивает активный пункт меню и ставит `aria-current="page"`;
   - `renderAuthState()` — переключает блоки «гость»/«пользователь» в шапке и вешает обработчик выхода;
   - `openModal(id)` / `closeModal(id)` — обёртки над `bootstrap.Modal.getOrCreateInstance`.

## 8. Ключевые механизмы работы приложения

Этот раздел — самый важный для подготовки к защите: здесь объясняется, как всё устроено «под капотом».

### 8.1. Пути к ресурсам и `data-root`

**Проблема.** Главная страница лежит в корне (`index.html`), а остальные — в подпапке `pages/`. Поэтому относительный путь к ресурсу с главной — `assets/img/sprite.svg`, а с внутренней страницы — уже `../assets/img/sprite.svg`. Хардкодить два варианта путей в JS неудобно и легко ошибиться.

**Решение.** На каждом `<body>` задан атрибут `data-root`:

- `index.html`: `<body data-root="">` — корень пустой;
- все страницы в `pages/`: `<body data-root="..">`.

Модуль `main.js` умеет читать этот атрибут и строить путь:

```js
export function root() {
  return document.body.dataset.root ?? '';
}

export function url(relativePath) {
  const base = root();
  return base ? `${base}/${relativePath}` : relativePath;
}
```

Теперь в JS всегда указывается путь «от корня проекта» (`url('pages/recipe.html')`, `url('assets/img/sprite.svg')`), а фактический префикс подставляется автоматически. Это же решение позволяет сайту работать на GitHub Pages в подпапке репозитория без изменения кода.

### 8.2. Авторизация

**Модель.** В ЛР1 авторизация полностью клиентская. Это осознанное упрощение: имитация закрытого API — тема ЛР2.

**Регистрация** (`auth.js`, `initRegisterForm`):

1. Форма перехватывает `submit` и вызывает `event.preventDefault()`.
2. Сбрасывается предыдущее состояние валидации (`resetValidation`).
3. Последовательно проверяются поля:
   - имя — минимум 2 символа;
   - e-mail — регулярным выражением `/^[^\s@]+@[^\s@]+\.[^\s@]+$/` и на уникальность (`emailExists`);
   - пароль — минимум 8 символов;
   - повтор пароля — совпадает с паролем;
   - чекбокс согласия — установлен.
4. Каждое поле получает класс `is-valid` или `is-invalid` (Bootstrap-стили) и сообщение в `invalid-feedback`.
5. Если всё корректно — создаётся объект пользователя с id вида `local-<timestamp>` (чтобы не столкнуться с числовыми id статических пользователей), сохраняется через `addLocalUser`, сразу открывается сессия (`setSessionUserId`) и выполняется переход в личный кабинет.

**Вход** (`auth.js`, `initLoginForm`):

1. Проверяется корректность e-mail и непустой пароль.
2. Отдельно обрабатывается демо-аккаунт `demo@recipehub.ru` / `demo1234` — он доступен всегда, даже если `localStorage` пуст (удобно для проверки преподавателем).
3. Иначе среди `getAllUsers()` ищется аккаунт с таким e-mail, и сверяется пароль.
4. При несовпадении показывается alert-блок «Неверный e-mail или пароль».
5. При успехе id пользователя пишется в сессию, и происходит переход в профиль.

**Сессия.** Хранится в `localStorage` под ключом `rh_session` — это просто id пользователя. Функция `getCurrentUser()` в `main.js` по этому id находит полный объект пользователя. Выход (`data-logout`) вызывает `clearSession()` и редирект на главную.

**Синхронизация шапки** (`main.js`, `renderAuthState`):

```js
document.querySelectorAll('[data-auth-guest]').forEach((block) => {
  block.hidden = Boolean(user);
});
document.querySelectorAll('[data-auth-user]').forEach((block) => {
  block.hidden = !user;
});
```

То есть на всех страницах автоматически показывается либо пара кнопок «Вход/Регистрация», либо меню пользователя с его именем.

**Защита страницы профиля** (`auth.js`, `guardProfilePage`): если в сессии нет пользователя, включается предупреждение `data-profile-guest`, а сам кабинет (`data-profile-page`) остаётся скрытым.

### 8.3. Рендер карточек и защита от XSS

Карточка рецепта формируется как строка HTML (`recipeCardTemplate`) и вставляется через `innerHTML`. Поскольку часть данных — пользовательские (названия, описания, имена, комментарии), весь такой текст прогоняется через `escapeHtml`:

```js
export function escapeHtml(value) {
  return String(value)
    .replaceAll('&', '&amp;')
    .replaceAll('<', '&lt;')
    .replaceAll('>', '&gt;')
    .replaceAll('"', '&quot;')
    .replaceAll("'", '&#39;');
}
```

Это предотвращает XSS: даже если пользователь создаст рецепт с названием `<script>alert(1)</script>`, оно отобразится как обычный текст, а не выполнится.

Карточка содержит:

- ссылку-обёртку на страницу рецепта (`url('pages/recipe.html?id=' + recipe.id)`);
- изображение-заглушку с классом `rh-card-image`;
- бейдж типа блюда и подпись сложности;
- заголовок `<h3>` с классом `stretched-link` (кликабельна вся карточка, но ссылка одна — это правильнее с точки зрения доступности, чем вкладывать ссылки друг в друга);
- имя автора;
- время (с иконкой часов) и число лайков (с иконкой сердца);
- бейдж «Сохранён», если рецепт в закладках.

### 8.4. Социальные функции (`social.js`)

Все четыре действия работают по одному принципу: **проверка авторизации → переключение состояния в localStorage → синхронизация кнопки**.

**Лайки** (`initLikeButtons`, `syncLikeButton`):

```js
function syncLikeButton(button, recipe) {
  const active = getLikes().includes(recipe.id);
  const count = recipe.likes + (active ? 1 : 0);
  button.classList.toggle('is-active', active);
  button.setAttribute('aria-pressed', String(active));
  // ...обновление счётчика и текста
}
```

Число лайков = базовое значение рецепта плюс 1, если текущий пользователь поставил лайк. Класс `is-active` подсвечивает кнопку фирменным цветом, а `aria-pressed` сообщает состояние скринридеру.

**Закладки** (`initBookmarkButtons`) — та же логика, текст кнопки меняется «Сохранить» ↔ «Сохранён».

**Подписки** (`initSubscribeButtons`) — переключатель «Подписаться» ↔ «Вы подписаны», состояние по id автора.

**Комментарии** (`initComments`):

- статические комментарии (`getCommentsByRecipe`) объединяются с локально добавленными (`getLocalComments`);
- список рендерится через `commentTemplate`, каждый комментарий экранируется;
- при отправке формы проверяется авторизация и непустой текст, затем комментарий пишется в localStorage с датой `new Date().toISOString()`, список и счётчик перерисовываются.

**Без авторизации** любое действие показывает `alert` с просьбой войти — данные при этом не меняются.

### 8.5. Личный кабинет (`profile.js`)

**Инициализация:**

```js
function init() {
  const page = document.querySelector('[data-profile-page]');
  if (!page) return;               // не страница профиля
  const user = getCurrentUser();
  if (!user) return;               // предупреждение покажет auth.js
  page.hidden = false;
  fillFilterOptions();             // для select-ов в модалке нового рецепта
  renderProfileHeader(user);
  renderPublished(user);
  renderSaved();
  renderSubscriptions();
  initNewRecipeForm(user);
  initEditProfileForm(user);
}
```

**Три коллекции:**

- **Публикации** — все рецепты, где `authorId` совпадает с id пользователя (сюда попадают и созданные через модалку);
- **Сохранённые** — рецепты, чьи id есть в списке закладок;
- **Подписки** — карточки авторов, на которых подписан пользователь; если список пуст, показывается подсказка со ссылкой на поиск.

**Создание рецепта** (`initNewRecipeForm`): валидируется название, ингредиенты разбиваются по запятой, шаги — по переводу строки. Создаётся объект рецепта с id `local-<timestamp>`, картинкой-заглушкой, `likes: 0`, сохраняется через `addLocalRecipe`, модалка закрывается, список публикаций обновляется без перезагрузки.

**Редактирование профиля** (`initEditProfileForm`): проверяется имя, изменения (имя, био) сохраняются через `saveProfileOverride` в отдельную «накладку» над статическими данными. Благодаря этому можно править даже статические аккаунты (включая демо), не изменяя `data.js`. После сохранения данные на странице и имя в шапке обновляются без перезагрузки.

### 8.6. Страница рецепта (`recipe.js`)

**Определение рецепта.** id берётся из адреса:

```js
function getRecipeIdFromUrl() {
  return new URLSearchParams(window.location.search).get('id');
}
```

Затем рецепт ищется среди всех (статические + локальные). Если не найден — показывается блок `data-recipe-not-found`.

**Рендер** (`renderRecipe`): заполняются заголовок, мета-данные, описание, ингредиенты и шаги. Шаги получают нумерованные кружки; номер помечен `aria-hidden="true"` (для скринридера список остаётся упорядоченным `<ol>`, а декоративный кружок не дублируется). Заголовок документа тоже обновляется: `document.title = `${recipe.title} — RecipeHub``. Видео-блок включается только при наличии `videoUrl`.

**Привязка соц. действий.** В разметке страницы кнопки лайка/закладки/подписки не содержат id заранее (страница одна на все рецепты). Поэтому `recipe.js` проставляет их в момент рендера:

```js
view.querySelector('[data-like-recipe]').dataset.likeRecipe = recipe.id;
view.querySelector('[data-bookmark-recipe]').dataset.bookmarkRecipe = recipe.id;
```

После этого модуль `social.js`, который инициализируется на том же событии `DOMContentLoaded`, находит кнопки по `data-*`-атрибутам и настраивает их. Комментарии аналогично привязываются через `dataset.commentsList`.

**Кнопка «Поделиться»** (`initShareButton`) использует Clipboard API:

```js
await navigator.clipboard.writeText(input.value);
button.textContent = 'Скопировано';
```

Через 1,5 секунды текст кнопки возвращается. Если Clipboard API недоступен (например, на `http://` вместо `https://`), в `catch` выполняется выделение текста в поле, чтобы пользователь скопировал вручную.

### 8.7. Модальные окна

Модалки открываются декларативно средствами Bootstrap — через атрибуты `data-bs-toggle="modal"` и `data-bs-target="#..."`. JS нужен только для программного закрытия после успешного сохранения формы:

```js
export function closeModal(id) {
  const element = document.getElementById(id);
  if (!element) return;
  bootstrap.Modal.getOrCreateInstance(element).hide();
}
```

`getOrCreateInstance` (а не `new bootstrap.Modal`) выбран потому, что он возвращает уже существующий экземпляр модалки, если тот был создан Bootstrap при первом открытии, и не создаёт дубликатов.

### 8.8. Фильтрация и сортировка (`filterRecipes`)

Функция принимает объект фильтров и последовательно применяет их:

```js
let result = getAllRecipes().filter((recipe) => {
  if (filters.dishType && recipe.dishType !== filters.dishType) return false;
  if (filters.difficulty && recipe.difficulty !== filters.difficulty) return false;
  if (filters.maxTime && recipe.timeMinutes > Number(filters.maxTime)) return false;

  if (query) {
    const haystack = `${recipe.title} ${recipe.description}`.toLowerCase();
    if (!haystack.includes(query)) return false;
  }

  if (ingredient) {
    const hasIngredient = recipe.ingredients.some((item) =>
      item.toLowerCase().includes(ingredient),
    );
    if (!hasIngredient) return false;
  }

  return true;
});
```

- тип блюда и сложность — точное совпадение;
- время — «не более» указанного;
- текстовый запрос — подстрока в названии **или** описании (регистронезависимо);
- ингредиент — подстрока в любом из ингредиентов.

Затем применяется сортировка (`likes`, `time-asc`, `time-desc`, по умолчанию — по дате создания, новые сверху). Результат рендерится, а счётчик обновляется:

```js
counter.textContent = `Найдено рецептов: ${list.length}`;
```

```css
  --rh-font-family: system-ui, -apple-system, "Segoe UI", Roboto, ...;

  --rh-radius: 0.5rem;
  --rh-radius-sm: 0.375rem;
  --rh-shadow-sm: 0 0.125rem 0.25rem rgba(0, 0, 0, 0.075);

  --rh-card-image-height: 12rem;
}
```

Это осознанный задел под **домашнюю работу 3** (темизация сайта средствами CSS-переменных): чтобы добавить тёмную тему, достаточно переопределить значения этих переменных, не трогая стили. Фирменный цвет `#b4552d` (терракотовый) выбран как «кулинарный» акцент, гармонирующий с нейтральной палитрой Bootstrap.

### 9.2. `style.css` — минимальный кастомный слой

Принцип: **сначала штатные классы Bootstrap, свой CSS — только там, где Bootstrap не закрывает задачу.** Описано 9 блоков:

1. `body` — применяет переменные шрифта, фона и цвета текста.
2. **Хак для `hidden` в шапке.** Утилиты Bootstrap (`.d-flex`) и атрибут `[hidden]` конфликтуют: оба используют `!important`, но `.d-flex` идёт ниже в `bootstrap.min.css` и побеждает, из-за чего скрытые кнопки оставались видимыми. Исправляется явным правилом:

   ```css
   [data-auth-guest][hidden],
   [data-auth-user][hidden] {
     display: none !important;
   }
   ```

   Это тонкий момент, который стоит помнить: атрибут `hidden` перебивается `display`-утилитами, если не повысить специфичность.
3. `.rh-link-reset` — убирает подчёркивание и наследует цвет у ссылок-обёрток карточек.
4. `.rh-card-image` — фиксированная высота обложки (`--rh-card-image-height`) и `object-fit: cover` для аккуратного кадрирования.
5. `.btn-rh-primary` — фирменная кнопка. Переопределяет не цвет напрямую, а CSS-переменные Bootstrap (`--bs-btn-bg`, `--bs-btn-hover-bg` и т.д.), поэтому кнопка корректно работает во всех состояниях (обычное, наведение, нажатие, фокус).
6. `.rh-icon` — размер иконки `1em` (масштабируется вместе с текстом) и выравнивание по базовой линии.
7. `.rh-step-number` — круглый номер шага приготовления.
8. `.rh-placeholder` — серый блок-заглушка (используется для аватара).
9. `.rh-action-btn.is-active` — активное состояние кнопок лайка/сохранения; `.rh-comment` — разделитель между комментариями; `.rh-page` — минимальная высота основной области.

## 10. SVG-спрайт иконок

Все иконки вынесены в один файл `assets/img/sprite.svg` (это фактически досрочное выполнение **домашней работы 4**). Спрайт содержит **15 символов**:

- линейные (`stroke="currentColor"`): `search`, `user`, `users`, `clock`, `plus`, `edit`, `logout`, `filter`, `eye`, `close`;
- заливные (`fill="currentColor"`): `heart`, `bookmark`, `chat`, `star`, `play`.

Подключение одной иконки выглядит так:

```html
<svg class="rh-icon" aria-hidden="true">
  <use href="../assets/img/sprite.svg#icon-search"></use>
</svg>
```

**Почему атрибуты заданы прямо на `<symbol>`.** При рендере через `<use>` содержимое `<symbol>` наследует стили не совсем так, как обычный инлайновый SVG. Чтобы иконки гарантированно отображались (не превращались в залитые чёрные фигуры или, наоборот, в невидимые контуры), параметры `fill`/`stroke` и `stroke-width` заданы внутри каждого `<symbol>`, а цвет — через `currentColor`, то есть наследуется от текста родителя.

**Доступность.** Декоративные иконки рядом с текстом помечены `aria-hidden="true"` — скринридер их не озвучивает, потому что смысл несёт соседний текст (например, иконка часов + «15 мин»). Сама заглушка `recipe-placeholder.svg` имеет `role="img"` и `aria-label`.

**Задел на будущее.** 8 иконок спрайта пока не используются в разметке — они добавлены с запасом под последующие работы (профиль, уведомления и т.п.). Это нормально и не является ошибкой.

## 11. Адаптивность и доступность

### 11.1. Адаптивность

Адаптивность обеспечивается штатной сеткой Bootstrap и контрольными точками:

- **Навигация:** `navbar-expand-lg` — на экранах уже `lg` меню сворачивается в «бургер» с `collapse`.
- **Карточки рецептов:** `row-cols-1 row-cols-md-2 row-cols-lg-3` (главная) и `row-cols-1 row-cols-md-2 row-cols-xl-3` (поиск) — от одной колонки на телефоне до трёх на широких экранах.
- **Формы входа/регистрации:** `col-12 col-md-8 col-lg-5/6` — на мобильных во всю ширину, на десктопе — аккуратная узкая колонка.
- **Поиск:** панель фильтров `col-12 col-lg-3`, результаты `col-12 col-lg-9`; панель фильтров «прилипает» при прокрутке на больших экранах (`sticky-lg-top`).
- **Карточка рецепта:** `col-12 col-lg-8` + `col-12 col-lg-4`.
- **Изображения:** `img-fluid`, обложки — с `object-fit: cover` фиксированной высоты.

### 11.2. Доступность (задел под ДЗ2)

Уже сейчас заложены элементы, которые пригодятся при выполнении домашней работы по доступности:

- семантические теги `header`, `nav`, `main`, `section`, `article`, `aside`, `footer`;
- у навигации `aria-label="Основная навигация"`, у кнопки-бургера — `aria-controls`, `aria-expanded`, `aria-label`;
- активный пункт меню получает `aria-current="page"`;
- у всех полей форм есть связанные `<label for="...">`;
- у декоративных иконок `aria-hidden="true"`;
- у кнопок-переключателей (`лайк`, `сохранение`, `подписка`) есть `aria-pressed`, отражающий состояние;
- у счётчика результатов `aria-live="polite"` — изменение числа найденных рецептов озвучивается;
- у модалок есть `aria-labelledby`, `aria-hidden`, кнопки закрытия с `aria-label="Закрыть"`;
- у хлебных крошек — `aria-label="breadcrumb"` и `aria-current="page"` на последнем элементе;
- у полей — `autocomplete` (`email`, `current-password`, `new-password`, `name`) для автозаполнения и удобства;
- у формы быстрого поиска на главной — `role="search"`.

Это даёт хорошую стартовую точку для ДЗ2: останется пройтись инструментами (Firefox Accessibility Inspector, Lighthouse) и устранить замечания.

## 12. Хранение данных в localStorage

Все ключи имеют префикс `rh_` (RecipeHub) во избежание конфликтов:

| Ключ | Что хранит | Тип значения |
|---|---|---|
| `rh_session` | id текущего авторизованного пользователя | строка или число |
| `rh_users` | зарегистрированные на устройстве аккаунты | массив объектов |
| `rh_profile_overrides` | правки имени/био для любого пользователя | объект `{ id: {name, bio} }` |
| `rh_recipes` | рецепты, созданные пользователем | массив объектов |
| `rh_likes` | id рецептов, которым поставлен лайк | массив чисел |
| `rh_bookmarks` | id сохранённых рецептов | массив чисел |
| `rh_subscriptions` | id авторов, на которых оформлена подписка | массив чисел |
| `rh_comments` | локально добавленные комментарии | массив объектов |

Важно понимать: `localStorage` привязан к origin (домен + порт), поэтому данные не переносятся между `localhost:8000` и `localhost:3000`. Функция `resetAll()` позволяет полностью очистить состояние при отладке.

## 15. Известные ограничения и задел на ЛР2

### Ограничения текущего этапа

1. **Данные статические.** Рецепты и пользователи «зашиты» в `data.js`, изменяются только через интерфейс (создание рецепта/профиля) и сохраняются локально.
2. **Авторизация клиентская.** Пароли хранятся в открытом виде в `localStorage` — это допустимо только для учебной имитации и будет заменено в ЛР2.
3. **Состояние не синхронизируется между устройствами** — оно привязано к браузеру.
4. **Чекбокс «Запомнить меня»** на странице входа присутствует в разметке, но не влияет на логику (сессия и так живёт в `localStorage` до выхода).
5. **Видео** — для двух рецептов указаны внешние ссылки-заглушки; при желании легко заменить на реальные.
6. **`alert()` при попытке соц. действия без входа** — простое, но не самое изящное решение; в дальнейшем его можно заменить на модальное окно или toast.

### Задел на ЛР2 («Взаимодействие с внешним API»)

- структура данных в `data.js` приближена к ответам API (ссылки по id, а не дублирование сущностей);
- весь доступ к состоянию изолирован в `storage.js` — при переходе на сервер достаточно заменить его реализацию (или добавить слой `api.js`), не переписывая страничные модули;
- формы уже собирают данные в структуры, близкие к телу запроса;
- `main.js` содержит единые точки `getAllRecipes`/`getAllUsers`/`getCurrentUser`, которые можно перевести на асинхронные запросы;
- модульность и отсутствие жёстких связей упростят добавление axios и мокового JSON-сервера.

### Задел на домашние работы

- **ДЗ2 (доступность):** уже есть семантика и ARIA — останется проверить инструментами и дополнить.
- **ДЗ3 (темизация):** CSS-переменные собраны в `variables.css`; добавление тёмной темы сведётся к переопределению переменных.
- **ДЗ4 (SVG-спрайт):** спрайт уже создан и используется (15 иконок).
- **ЛР3 (Vue SPA):** разбиение на модули по зонам ответственности (`данные / хранилище / утилиты / страничная логика`) почти напрямую ложится на компоненты, composables и store Vue.
